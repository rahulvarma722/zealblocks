# Styles

Three layers, each with a different job.

| Layer | File | Loaded where |
|---|---|---|
| Shared | `src/*/style.scss` | Front end **and** editor canvas |
| Editor only | `src/*/editor.scss` | Editor only — editing affordances |
| Per-instance | generated in `render.php` | Style-engine store, printed via `wp_add_inline_style()` |

`wp-scripts` compiles these to `build/*/style-index.css` and
`build/*/index.css`, which `block.json` declares as `style` and `editorStyle`.
RTL variants are emitted automatically and picked up by core.

## Class naming

```
.wp-block-zealblocks-button              block root
.wp-block-zealblocks-button__text        label span
.wp-block-zealblocks-button__icon        inline SVG
.wp-block-zealblocks-button.has-icon-left
.wp-block-zealblocks-buttons             container root
.zealblocks-btn-<hash>                         per-instance, generated
```

`wp-block-<namespace>-<name>` is core's own convention, generated by
`useBlockProps()` in the editor and `get_block_wrapper_attributes()` on the
front end. The `__text` / `__icon` children are ours.

`.zealblocks-btn-<hash>` is generated per *value set*, not per instance — the hash is
derived from the stored values, so two buttons with identical width and icon
size collapse onto one rule instead of emitting a near-duplicate each.

## Deliberately low specificity

One class, no `!important`, no IDs. These are defaults that core's block
supports must be able to override — core writes responsive and state rules at
specificity `0,1,0` with `!important`, so anything stronger here would defeat
them. Every declaration that a `supports` flag can override is marked as such
in a comment.

## Per-viewport styling — the core mechanism

This is the plugin's reason to exist, so it is worth understanding.

### Where the values live

Not in attributes of our own. Inside core's `style` attribute, under a
namespaced key, in core's viewport-state shape:

```json
{
  "zealblocks":  { "width": "200px", "iconSize": "1.5em" },
  "@tablet":   { "zealblocks": { "width": "150px" } },
  "@mobile":   { "zealblocks": { "width": "100%", "iconSize": "2em" } }
}
```

`style` is declared by core as a free-form `{ type: 'object' }` attribute with
no key allow-list, so a namespaced key survives serialisation untouched. Core
generates CSS only for paths it *owns*, so nothing of ours is emitted by core —
which is why `render.php` has to do it.

Storing it this way is what makes the control behave like a core one: the state
the user is editing decides which value is read and written, so with Responsive
styles off only the base value is ever visible or editable.

### Desktop is the base layer, not a third band

A value set on Desktop carries no media query and applies at every width.
`@tablet` and `@mobile` are overrides on top of it.

That asymmetry is core's model, and following it is what makes **Mobile fall
back to Desktop rather than to Tablet**.

### The media queries come from core

`Helper::media_queries()` resolves them, from
`\WP_Theme_JSON::get_viewport_media_queries()` — public and documented
(`@since 7.1.0`), reads `settings.viewport` from theme.json, and returns exactly
the bands core uses for its own per-viewport output:

```css
@mobile   @media (width <= 480px)
@tablet   @media (480px < width <= 782px)
```

Note the shape: **mutually exclusive ranges**, not stacked `max-width`
queries. That is what makes mobile fall back to the base layer rather than to
tablet. Reimplementing them with `max-width` would silently reintroduce a
tablet-into-mobile cascade and disagree with every core control on the same
block.

Change your breakpoints in theme.json and Zealblocks follows, because it never
had its own. `Helper::FALLBACK_BREAKPOINTS` covers pre-7.1 only, kept identical to core's
defaults so a site that upgrades sees no shift. `Helper::breakpoint( 'mobile' )`
gives the raw width for anything that needs the number rather than the query.

### Styling a descendant — the CSS-variable indirection

Two properties, two very different destinations.

**`width`** is emitted as a real declaration on the block root. Simple: the
root is the one element inline styles and `get_block_wrapper_attributes()` can
reach.

**`iconSize`** cannot be, because the icon is a **child**. Nothing available
here selects a child: `get_block_wrapper_attributes()` writes to the root, and
so does core's own per-viewport CSS unless the block declares feature selectors
in `block.json`.

So the value is emitted as a **custom property on the root**, and `style.scss`
spends it on the child:

```scss
&__icon {
  width:  var(--zealblocks-button-icon-size, 1em);
  height: var(--zealblocks-button-icon-size, 1em);
}
```

The media queries stay on the root, so the icon becomes per-viewport without a
single descendant selector being generated. One indirection buys the whole
capability. The fallback keeps the icon visible before any value is set.

### Value validation, not escaping

`Responsive_Styles::is_safe_length()` allow-lists `<number><unit>`:

```
px  %  em  rem  vw  vh
```

An allow-list rather than escaping, because escaping cannot make
`expression(…)` or an unbalanced `)` safe inside a declaration.

**Negatives are rejected by default.** Both properties this serves feed
non-negative CSS, so `-50px` only ever produced a declaration the browser
discards. An `$allow_negative` flag exists because that is a property of the
caller — reused for `margin`, it should pass `true`.

### How the per-instance CSS reaches the page

It is **not** printed inline. `render.php` hands the rules to
`wp_style_engine_get_stylesheet_from_css_rules()` with `context => 'zealblocks'`,
which stores them. Core flushes every store in `wp_enqueue_stored_styles()` —
hooked to `wp_enqueue_scripts` and to `wp_footer` — through
`wp_register_style()`, `wp_add_inline_style()` and `wp_enqueue_style()`, as one
`<style id="wp-style-engine-zealblocks-inline-css">`. Block themes render the
template before the head is printed, so it lands in `<head>`; classic themes get
it in the footer.

This is exactly the path core's own per-viewport CSS takes
(`block-supports/states.php` makes the same call with
`context => 'block-supports'`), so the block is at parity with the core controls
beside it. The Plugin Review Team asked for this in place of an inline `<style>`
element; making the change also removed a `phpcs:ignore`.

The media query travels as `rules_group`, verbatim. Core's range syntax —
`@media (480px < width <= 782px)` — contains `<`, so it must never pass through
`wp_strip_all_tags()` or `esc_attr()`, both of which mangle it; the style engine
takes it as data. Values are still allow-listed by `is_safe_length()` before
they get anywhere near it, and the selector is generated from an md5, so
nothing user-controlled reaches the stylesheet.

The store de-duplicates by selector: two buttons with identical values share a
hash class and therefore a single rule.

## The editor side

`src/button/responsive-width/` holds the control.

| File | Job |
|---|---|
| `constants.js` | The inspector group, storage keys, breakpoint map, units, diagnostics flag |
| `style-value.js` | Read/write/resolve a value in a given state layer |
| `use-style-state.js` | Detect **which** state the editor is currently editing |
| `index.js` | The ToolsPanel rows themselves |

`use-style-state.js` is the hard part. Core knows the answer precisely, but
`isResponsiveEditing()` and `getSelectedBlockStyleState()` are *private*
selectors reachable only via `unlock()`, which throws for anything that is not
a core package. So the state is inferred from three public, reactive signals —
the selected device, whether core is rendering its style-state toolbar, and
whether the inspector is showing its normal style view — by mounting invisible
probes inside the slots that gate them and letting core's own render decisions
become the input.

`SHOW_DIAGNOSTICS` in `constants.js` renders a live readout of all of that into
the Styles tab. It is `false` for release, and webpack's dead-code elimination
strips the block entirely. Flip it to `true` and rebuild when working on the
detection.

The full reasoning, what else was tried, and why the `styles` inspector group
is a trap, is in
[Responsive styles experiment](RESPONSIVE-STYLES-EXPERIMENT.md).

## Editor/front-end parity

Both read the same rule from `style.scss`, and the editor mirrors the front
end's class decisions — `has-icon-left`, the per-instance custom property — so
what the canvas shows is what ships. Icon position uses `flex-direction:
row-reverse` rather than `order`, so the DOM keeps text-then-icon and the
accessible name is unaffected by visual position.
